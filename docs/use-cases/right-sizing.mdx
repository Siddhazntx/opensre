# Right-Sizing Infrastructure with OpenSRE

In modern cloud environments, engineering teams frequently default to larger Amazon EC2 instances, generous ECS task sizes, or high Kubernetes CPU and Memory requests to ensure stability.

While this prevents out-of-memory (OOM) errors and CPU throttling, it creates a massive anti-pattern: chronic over-provisioning.

Over time, these under-utilized EC2, ECS, and Kubernetes workloads accumulate, driving unnecessary and bloated cloud expenditure.

Right-sizing is the SRE practice of continuously analyzing actual usage patterns and adjusting resource allocations to match reality.

OpenSRE automates this workflow by directly querying your observability stack, running statistical analysis on historical telemetry, and surfacing exact CPU and memory headroom metrics.

## Why Right-Sizing Matters

Infrastructure is commonly over-provisioned because teams optimize for reliability during production incidents and rarely revisit sizing decisions later.

This leads to:

- Idle EC2 instances
- Oversized ECS task definitions
- Excessive Kubernetes CPU requests
- Wasted memory reservations
- Poor autoscaling efficiency

Without continuous optimization, infrastructure waste grows significantly over time.

Right-sizing helps organizations:

- Reduce monthly cloud expenditure
- Improve Kubernetes cluster utilization
- Increase scheduling efficiency
- Prevent infrastructure sprawl
- Optimize autoscaling behavior
- Improve operational visibility

## Supported Telemetry Integrations

To perform right-sizing investigations, OpenSRE leverages your existing metric stores.

Ensure you have at least one of the following integrations configured:

### Prometheus

The standard for Kubernetes workloads.

OpenSRE queries metrics from:

- `kube-state-metrics`
- `node-exporter`
- `cadvisor`

This allows comparison between configured Pod requests/limits and actual runtime usage using metrics such as:

- `container_cpu_usage_seconds_total`
- `container_memory_working_set_bytes`
- `kube_pod_container_resource_requests`
- `kube_pod_container_resource_limits`

### AWS CloudWatch

Essential for raw AWS infrastructure visibility.

OpenSRE fetches:

- EC2 CPU utilization
- ECS task resource metrics
- Network throughput
- Disk activity
- Autoscaling activity

No additional agents are required.

### Datadog

Connects through the Datadog API to retrieve:

- Host-level metrics
- APM telemetry
- Kubernetes resource utilization
- Custom infrastructure tags

Useful for hybrid cloud environments and multi-cluster deployments.

### Grafana

Connects to existing Grafana data sources to analyze historical workload behavior directly from your dashboards.

This allows OpenSRE to reuse existing telemetry pipelines without duplicating infrastructure.

## Recommended Investigation Prompts

You can trigger right-sizing workflows in the OpenSRE interactive shell using natural language.

### EC2 Investigation

```text
Analyze all EC2 instances in the `us-east-1` production account.
Identify instances where max CPU utilization has not exceeded 15%
and memory usage stayed under 30% over the last 14 days.
Return a table with: instance id, instance type, average CPU, max CPU, average memory, max memory, launch date, and a recommended instance type when applicable.
```

### ECS Investigation

```text
Analyze ECS services in the `prod-ecs` cluster over the last 14 days.
Identify task definitions and services where configured CPU or memory reservations
are consistently under-utilized (e.g. 25% of reservation or lower on the 95th percentile).
Return service name, task definition, current reservation (CPU/memory), 95th percentile usage, and suggested reservation adjustments.
```

### Kubernetes Investigation

```text
Analyze Kubernetes namespaces `production` and `staging` for pods with over-provisioned requests/limits.
Compare container `requests` and `limits` to observed runtime usage (95th percentile) over the last 14 days.
List pods where request-to-usage ratio exceeds 4x (or 2x for critical workloads), and suggest new request/limit values.
Also flag containers that show OOMKilled events or sustained CPU throttling for further investigation.
```

## Actionable Next Steps

- Run a discovery pass in a non-production account to validate recommendations and identify false positives.
- Create small, incremental change sets (canary/gradual downsize) rather than global mass changes.
- Monitor the changed instances/pods for 7–14 days and roll back if sustained CPU or memory exceed 80%.
- Integrate periodic right-sizing runs into your cost ops pipeline and add alerts for unexpected regression.
- Document any manual adjustments in the runbook and record rationale for future audits.
